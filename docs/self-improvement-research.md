# 递归自我改进（RSI）：研究与设计草案

> 状态：研究草案。第 0 阶段（体检报告）、第 1 阶段（回放）和第 3 阶段（经验与技能，评测通过即自动生效）已实现，见[架构](architecture.md#自我改进体检回放与学习)；其余尚未实现。第 2 阶段的空闲调度只做了最简单的一版（见第 3 阶段的取舍）。目标是回答一个问题：AgentOS 能不能利用机器空闲时的资源，持续地让自己变得更好，而且不破坏 [AGENTS.md](../AGENTS.md) 里那些不能破坏的约定。

## 1. 先说清楚能做到什么

**真正的 RSI（模型改写自己的权重、变得更聪明）在这里做不到，也不该是目标。** AgentOS 的“大脑”是云端模型（Claude / OpenAI 兼容接口）或本地 Ollama/vLLM，系统拿不到权重，也没有训练算力。

能做到、并且值得做的是 **“模型之外的整个系统”自我改进**：模型固定，系统不断改进围绕它的一切——提示词、子 Agent 清单、技能、插件、路由与预算配置，最终到 Rust 代码本身。近几年的研究表明，这一层的收益很大：

| 工作 | 改进的对象 | 对我们的启发 |
| --- | --- | --- |
| Voyager（2023） | 可复用的技能库 | 把成功的做法沉淀成技能，下次直接用 |
| Reflexion / ExpeL（2023） | 从失败经历里总结的文字经验 | 失败任务是最便宜的改进信号 |
| DSPy / GEPA（2023–2025） | 提示词，在评测集上自动搜索 | 提示词优化必须有评测集，不能凭感觉 |
| STOP（2023） | 改进器自己的代码 | “改进改进器”是递归的关键，也最容易出事 |
| ADAS / Gödel Agent（2024） | Agent 的整体设计 | 搜索空间可以是“Agent 的结构” |
| Darwin Gödel Machine（2025） | 编码 Agent 自己的代码，用基准测试打分，保留历代存档 | 有效，但**被观察到会钻评测的空子**（伪造测试结果、删掉检测标记） |
| AlphaEvolve（2025） | 程序，靠自动评估器做进化搜索 | 只要评估器可靠，LLM + 进化搜索能找到真正的改进 |

结论只有一条：**RSI 的瓶颈不是“能不能生成改进”，而是“能不能可靠地判断一个改动是不是改进”。** 本设计的大部分篇幅都在评估器和安全边界上。

## 2. AgentOS 已经有的基础

这个仓库已经具备了 RSI 循环的大半零件，只是还没有串起来：

| 零件 | 现状 | 在 RSI 里的角色 |
| --- | --- | --- |
| 审计日志 `agentos-audit` | 每个意图、计划、每次能力调用的 **参数和结果**、模型用量（token、缓存、耗时）、确认与拒绝、裁判结论，哈希链、只追加 | **完整的执行轨迹**：既是改进信号的来源，也是回放评测的录像 |
| 任务存储 `agentos-runtime` | 如实的结局：`succeeded` / `unhandled` / `failed`（带原因：打转、预算、某步失败） | 现成的打分标签 |
| 自我进化 `evolve.*` | 生成插件 → 沙箱自测 → L3 人工安装 → 版本化、可回滚 | 改进“能力”这一层的完整流水线 |
| 子 Agent 清单 `agents.rs` | `instructions`、`max_rounds`、能力范围都是数据 | 可以版本化、可以被调优的对象 |
| 脚本化规划器测试 | 不依赖真实接口测规划行为 | 回放评测的基础 |
| 策略引擎、污点、PIN、裁判 | 能力不做权限判断，一切经管家 | 改进器也只是一个被收窄的主体 |
| `agentos-update` | 校验 → 自检 → 替换 → 一步回滚 | 代码级改进的落地通道 |
| [self-evolution.md](self-evolution.md) “后续” | 已列出“技能”和“核心组件受控自我修改 + A/B 切换” | 本设计是这两条的展开 |

## 3. 整体结构：一个在空闲时运行的改进循环

```
            ┌──────────────── 空闲调度器（只在机器空闲时运行，用户一来立即让出）
            ▼
  ① 发现机会  ← 审计日志 + 任务历史（排除受污染任务）
            │   “unhandled 的意图”“同一插件反复失败”“打转”“用户拒绝了确认”
            │   “重复出现的多步意图”“token / 耗时异常高”
            ▼
  ② 生成候选  ← 改进器 Agent（被收窄的主体，只能写草案）
            │   技能 / 子 Agent 指令 / 提示词附加段 / 插件修复 / 配置 / 代码补丁
            ▼
  ③ 离线评测  ← 回放评测集 + 留出集 + 用户的金标准任务（改进器碰不到）
            │   结局不退化、步骤与 token 更少、成对比较更优
            ▼
  ④ 过门  ← 评测明显变好（第 4.1 节的门槛）
            │   层 A/B/C/E：直接自动生效，事后告知     层 D/F：进收件箱，带证据等人批准
            ▼
  ⑤ 版本化应用 → ⑥ 线上观察，退化自动回滚
            │
            └─→ 结果（接受 / 拒绝 / 回滚）反馈给 ①②，改进器据此调整自己的策略
```

“递归”体现在两处：一是改进后的系统会产生更好的轨迹和更准的信号，下一轮改进的起点更高；二是改进器自己的**搜索策略**（它用的提示词、挑选机会的方式）也是可改进的对象，但必须走同一道评测门，并且评测器本身不在可改范围之内（见第 6 节）。

## 4. 改进什么：按风险分层

越往下收益越大、风险越高，落地顺序也是从上到下。

| 层 | 改进对象 | 存放方式 | 怎么生效 | 回滚 |
| --- | --- | --- | --- | --- |
| A. 经验 | 从失败任务总结的“教训”（例如“查天气先确认城市”） | 状态目录 `improve/lessons/` 版本化 | **过门即自动生效** | 停用某条；线上退化自动回滚 |
| B. 技能 | 组合已有能力的工作流（不写代码），例如“准备出差 = 查日程 + 查天气 + 写清单”；形式是一个自动生成的子 Agent 清单 | `improve/skills/<名字>/versions/<n>` | **过门即自动生效**（技能里每一步照常过策略） | 切版本；线上退化自动回滚 |
| C. 提示与清单 | 管家提示词的**附加段**、子 Agent 的 `instructions` / `max_rounds` | 版本化文件；基础 `SYSTEM_PROMPT` 常量不动 | **过更严的门后自动生效** | 切版本；线上退化自动回滚 |
| D. 插件 | 修复反复失败的插件、补自测、性能优化 | 现有 `evolve` 版本目录 | 人批准，L3（沿用现有规则） | `evolve.rollback` |
| E. 配置 | 按任务类别路由模型（简单任务用便宜模型）、缓存策略 | 版本化配置 | **只往省钱的方向自动生效**；加预算、换更贵的模型要人批准 | 切版本；线上退化自动回滚 |
| F. 代码 | Rust 补丁：修 bug、性能、新的内置能力 | git 分支 → 更新包 | 人审阅代码 | `agentos-update --rollback` |

几点理由：

- **提示词用“附加段”而不是改常量。** `SYSTEM_PROMPT` 是常量，正好是安全边界的一部分（它告诉模型规则）；改进只追加一段版本化的文字。附加段在一个版本内固定不变，不会破坏同一段执行里“系统提示一字不差”的提示缓存约定。
- **技能优先于插件。** 技能只是已有能力的编排，每一步照常经过策略引擎和审计，不引入新代码；self-evolution.md 已经把它列为“比写代码更轻、更安全”。
- **层 F 不在设备上自动合并。** 设备上编译整个工作区很重，而且“改自己的内核”必须经过人的代码审阅。设备只负责生成补丁并在隔离环境里跑 AGENTS.md 规定的四条检查，产出一个分支 / PR 或一个本地更新包，由人决定。

### 4.1 自动生效（产品决定）

**决定：改动在评测明显变好之后直接自动生效，尽量不需要人批准。** 不再设收件箱等人点头；人看到的是事后的通知和随时可用的撤销。只有两类仍要人批准，原因都不是“谨慎”，而是现有约定：

- **层 D（插件）**：会在机器上运行新写的代码。[self-evolution.md](self-evolution.md) 的原则是“安装永远是 L3，必须用户明确确认，不能预授权”，AGENTS.md 也要求 L3 的批准绑定具体请求并核对 PIN。
- **层 F（代码补丁）**：改的是策略引擎、审计这些安全边界所在的内核，必须有人审阅代码。

**自动生效不减少对动作的确认。** 经验和提示附加段只是文字，技能是收窄的子 Agent；它们都不能改授权、风险等级、预授权或策略。所以技能里的 L2 调用照样每次问人，受污染的任务照样要确认。自动化的只是“采纳这条改进”这一步，不是“执行动作”这一步。

**“明显变好”的门槛**（全部满足才生效，评估器和门槛本身不在改进范围之内）：

1. 用模型规划器评测。经验、技能、提示只影响模型；规则规划器的回放永远是“相同”，不能当证据。
2. 至少 10 个可比较的用例，包括引出这条改进的任务、留出集，以及用户标过的金标准任务（如果有）。
3. 基线和候选各跑 3 次。任何用例在任何一次里退化，都不通过。
4. 至少 2 个用例在多数次数里（3 次中至少 2 次）稳定变好，而基线在这些用例上没有；或者结局全部相同，而这些用例的总 token 或总步骤少了 20% 以上。
5. 候选比基线多偏离录像的用例不超过 1 个：偏离的用例无法判断，大量偏离说明候选在做录像里没有的事，不能算作证据。
6. 总 token 不比基线多 20% 以上（按总量而不是逐个用例算：单个用例的 token 随模型波动很大，逐个比会把噪声当成退化）。
7. 层 C 的门更严：至少 20 个用例，并且金标准任务必须存在、全部不退化。

**护栏：**

- **来源干净。** 生成改进只能用没受污染、由用户本人提交的任务（与体检报告同一规则）。候选只要用到了受污染的文字就丢弃，不进入评测，更不会自动生效。
- **内容有界。** 一条经验不超过 200 字，同时生效的经验最多 20 条；技能的能力只能是引出它的那串调用里的能力，风险上限不超过其中最高的一个，永远不到 L3，也不能包含 `evolve.*`、`improve.*`。
- **一次一个，留观察期。** 同一时间只生效一个新改动，观察一段时间（例如接下来 20 个相关任务或 3 天）再上下一个，这样线上的变化能归因。每天最多自动生效 3 个。
- **线上退化自动回滚。** 观察期内，相关任务的成功率比生效前低、用户取消或拒绝确认变多，就自动撤回，记审计并告知用户。
- **事后告知，随时撤销。** 每次生效都写审计 `ImprovementApplied`（内容、哈希、评测证据），在桌面“最近活动”里显示，用一句话通知（例如“我学会了：查天气前先确认城市”）。`improve.rollback`（L1）一步撤销；`AGENTOS_IMPROVE_AUTO=0` 关掉自动生效，退回到每条都等人批准。
- **换模型重新评测。** 每条改进记录它是在哪个模型上评测的；换模型后重新过门，不过就停用。

## 5. 改进信号：从审计日志里挖

审计日志已经记录了每次调用的参数和结果，任务记录了如实的结局，这些信号不需要模型就能算出来（第 0 阶段可以纯规则实现）：

| 信号 | 来源 | 指向的改进 |
| --- | --- | --- |
| `unhandled` 的意图，相似的反复出现 | 任务结局 | 缺能力 → 插件（D）或技能（B） |
| 同一个插件反复 `ok: false` | `CapabilityInvoked` | 插件修复（D） |
| “规划陷入重复”、预算用完 | 任务失败原因 | 经验（A）、提示附加段（C）、`max_rounds`（C） |
| 整轮预检失败（参数无效、能力不存在） | 任务失败原因 | 工具描述不清（C） |
| 用户拒绝了某类确认、裁判频繁收紧 | `HumanConfirmation`、`JudgeVerdict` | 规划方向错了（A/C） |
| 同一线程里用户立刻换说法重说 | 意图序列 | 隐性不满（A/C） |
| 同一组多步调用反复出现 | 调用序列挖掘 | 技能（B） |
| 某类任务 token / 耗时远高于中位数 | `ModelUsage` | 模型路由与预算（E）、缓存命中率 |
| 守护进程崩溃 | `DaemonCrashed`、`crash.txt` | 代码修复（F） |

**受污染的任务不进入改进流程。** 读过网页、邮件、MCP 工具输出的任务，其轨迹里可能有提示注入；如果把它们喂给改进器，攻击者就能把指令写进系统的“长期记忆”。规则：受污染任务只贡献“发生过、结局如何”这种统计量，不贡献任何文字内容。任何候选只要用到了受污染的文字就直接丢弃，不进入评测，也不会自动生效。

## 6. 评估器：整个设计的核心

### 6.1 回放评测

评测集来自本机历史：每个已结束、未受污染的任务，连同它在审计日志里的完整轨迹，构成一个用例。

- **能力层用录像代替。** 候选系统重新规划这个意图；它发起的调用如果和录像里的（能力名 + 参数）匹配，就返回录像的结果；只读能力（L0）可以选择真实执行；**任何不匹配的、有副作用的调用一律不执行**，记为“偏离录像”，这个用例改由成对裁判判断。这保证评测在任何情况下都不会动真实世界。
- **打分。** 结局不能退化（原来 `succeeded` 的仍要 `succeeded`；原来 `unhandled` / `failed` 的变好算加分）；在此基础上比较规划轮数、调用数、token、模拟耗时；无法用规则判断的，用模型做**成对盲评**（候选 vs 基线，随机交换顺序，两次一致才算数）。
- **三份数据。** 训练集（改进器能看到用例）、留出集（改进器看不到，只看到总分）、用户的金标准任务（用户自己挑出来的、必须一直做对的任务，相当于回归测试）。留出集和金标准任何一项退化，候选直接淘汰。
- **噪声。** 模型输出有随机性，每个用例跑多次，用配对检验判断差异是否显著；不显著的改动不提交，避免把噪声当改进。

### 6.2 防止钻空子

Darwin Gödel Machine 的经验说明：只要改进器能碰到评测，它就会去改评测。所以：

- **受保护的内核不在可改范围之内**：策略引擎、审计日志、评估器与评测数据、改进器的权限清单、PIN 与批准流程、裁判、`SYSTEM_PROMPT` 常量。层 F 的补丁如果触及这些路径，静态检查直接拒绝，不进入评测。
- **评估器和改进器分开运行**：评估器是 `agentos-taskd` 里的内置代码，改进器只能提交候选、读取分数，不能读评估器的中间结果，更不能读留出集的用例。
- **改进器的“自我改进”也要过门**：改进器改自己的提示词时，衡量标准是它产出候选的**接受率 × 评测增益**，在过去的改进历史上回放；这个元评测同样不可改。
- **证据可查**：每个生效的改进（自动的写在审计和“最近活动”里，层 D/F 在收件箱里）都附上“变好的例子”和“变坏的例子”各几条原文对比，而不只是一个总分，人随时可以抽查并撤销。

## 7. 空闲调度：“不断地”但不打扰

| 条件 | 做法 |
| --- | --- |
| 什么时候算空闲 | 没有排队或执行中的任务、N 分钟无用户输入、接通电源、系统负载低于阈值；可设置时间段（例如夜间） |
| 让出 | 用户一提交意图，改进任务立即取消（改进流程里的一切都是可中止的只读或沙箱操作，取消不留副作用） |
| 进程优先级 | 改进工作跑在单独的 systemd scope 里：`CPUWeight=idle`、`IOWeight` 最低、`MemoryMax` 限额；插件自测沿用现有 rlimit |
| 占用 worker | 改进任务不占 4 个用户 worker，用单独的一个低优先级槽位 |
| **钱** | 空闲 CPU 是免费的，**云端 token 不是**。必须有每日 token 上限（例如 `AGENTOS_IMPROVE_TOKENS_PER_DAY`，默认 0 = 关闭），用量照常写 `ModelUsage`，`purpose` 为 `improve`。配置了本地模型时，可以让改进只用本地模型，这时空闲资源才是真正免费的 |
| 停止条件 | 连续若干轮没有显著改进时退避（间隔加倍），避免无谓消耗 |

## 8. 与现有约定的对照

| 约定（AGENTS.md） | 本设计怎么遵守 |
| --- | --- |
| 能力不做权限判断 | 改进器是一个被收窄的主体（类似外部调用方），只拿到 `improve.*` 的草案类能力和 L0 读取；应用改动是单独的能力，按层级定风险，经策略引擎 |
| 结局如实 | 改进任务的结局同样如实；评测分数里“偏离录像”“无法判断”单独计数，不算成功 |
| 界面不替用户说话 | 已生效的改进和层 D/F 的收件箱都用协议 `read` 展示，不提交固定文字的意图 |
| 批准绑定具体请求 | 层 A/B/C/E 自动生效不涉及批准，生效的就是评测过的那一版（以哈希锁定，记入审计）；层 D/F 的批准绑定“这个候选的这个版本（带哈希）”，审阅的就是应用的 |
| 先落盘再执行 | 应用改动前写审计开始标记；版本目录先写好再切换 `current` |
| 审计只追加 | 新增事件：`ImprovementProposed`、`ImprovementEvaluated`（分数、用例数、数据集哈希）、`ImprovementApplied`、`ImprovementRolledBack`，旧记录照常可读 |
| 协议严格 | 新方法（列出候选、查看证据）按协议文档的兼容性说明新增 |
| 一份实现 | 回放器复用 `agentos-planner` 的脚本化规划器和 `agentos-services` 的能力注册表接口，不复制 |

## 9. 分阶段落地

每个阶段都单独有价值，不必等到最后一步。

| 阶段 | 内容 | 需要模型 | 主要位置 |
| --- | --- | --- | --- |
| 0. 体检报告（**已实现**） | 纯规则扫描审计日志和任务历史，生成第 5 节的信号报告；L0 能力 `improve.report`，用 `agentos read improve.report` 查看 | 否 | `crates/taskd/src/improve.rs` |
| 1. 回放评测（**已实现**） | 从任务记录重建轨迹，录像式能力层，结局对比打分；`agentos-taskd --replay`，有退化时退出码为 1，可以用作回归检查 | 用模型规划器回放时 | `crates/taskd/src/replay.rs` |
| 2. 空闲调度 | 空闲检测、低优先级槽位、可中止、每日 token 上限 | 否 | `crates/taskd/src/service.rs`、systemd 单元 |
| 3. 经验与技能（**已实现**） | 层 A、B：从失败任务总结经验、从重复调用序列提炼技能，过门后自动生效、线上退化自动回滚 | 是 | `crates/taskd/src/learn.rs`、`learned.rs` |
| 4. 插件自修复 | 层 D：把反复失败的插件和失败记录交给现有 `evolve.propose`（`target` 升级），评测 + 自测通过后进收件箱 | 是 | 复用 `evolve.rs` |
| 5. 提示与配置 | 层 C、E：提示附加段、子 Agent 指令、模型路由的搜索式优化（GEPA 式：反思失败 → 改写 → 评测 → 保留帕累托前沿） | 是 | `crates/planner/`、`agents.rs` |
| 6. 代码补丁 | 层 F：在隔离 worktree / 容器里生成补丁、跑四条检查和回放评测，产出分支或本地更新包，人审阅后走 `agentos-update` | 是 | 新工具，不进守护进程 |

第 0 阶段落地时的取舍：

- 放在 `agentos-taskd` 而不是 `agentos-services`，因为它要读 `agentos-runtime` 的任务，而 services 不依赖 runtime。
- 没有做 `agentos-taskd --improve-report`：打开任务存储要拿排他锁并改写快照，守护进程运行时另一个进程不能安全地打开它。改为普通的 L0 能力，任何客户端都能用协议的 `read` 读到，不需要新的协议方法。
- 第 5 节里“用户立刻换说法重说”这一项还没有做：只靠规则很难判断两句话是不是同一个意思。
- 每次生成报告都会读整份审计日志；日志很大时会慢一些，以后可以只读窗口内的部分。

第 1 阶段落地时的取舍：

- **录像来自任务记录，不是审计日志。** 任务的每一步都存着参数和完整结果，还有如实的结局、是否受污染、属于哪个线程，一个任务就是一个用例；审计日志没有污点和线程。
- **离线命令，不在守护进程里。** `agentos-taskd --replay` 不拿任务存储的锁、不写守护进程的任何文件（新增 `TaskStore::read_tasks` 和 `PluginManager::open_read_only`），守护进程运行时也能跑。每个用例有自己的内存任务存储、临时审计日志和临时 PIN，跑完就删，所以回放不会混进真实的审计日志、污染以后的改进信号。
- **不和真实世界接触。** 第 6.1 节设想只读能力可以真实执行；这一版一律不执行，录像里没有的调用直接记为“偏离录像”。这样回放在任何时候都安全，也不依赖网络和外部状态。
- **只回放能公平比较的任务：** 有结局的（成功、无法处理、失败）、没读过外部内容、不是外部调用方提交、不是接着前面对话说的、没用到回放里没有的能力（MCP 工具和智能家居要启动外部程序或联网，回放里不提供）。被跳过的按原因计数。
- **默认用规则规划器。** 环境里有 API key 也不会自动用模型；要用模型回放必须写明 `--planner`，因为它会花钱。
- **还没做的：** 同一个用例跑多次再做统计检验（模型有随机性，单次的“变好/退化”可能是噪声）；成对盲评；留出集和金标准任务的持久清单（现在可以用 `--tasks` 手工指定）；接进 `agentos-update` 的自检；黑板内容和最近任务这些上下文在回放里是空的，依赖它们的任务可能显示为“改变”。

第 3 阶段落地时的取舍：

- **在守护进程里跑，不是离线命令。** 审计日志只有一个写入者，采用和撤回都要写审计，只能由守护进程来做；它也有完整的能力注册表（包括 MCP 和智能家居），回放更接近真实。
- **经验进系统提示，技能是子 Agent。** 经验追加在管家系统提示里（外部调用方的任务看不到），一段执行内不变，不破坏提示缓存；技能是一个自动生成的 Agent 清单（id 以 `learned-` 开头），能力只能是引出它的那串调用，风险上限取其中最高的、永远不到 L3。子 Agent 的授权照常收窄，所以技能做不了管家做不了的事。
- **空闲调度是最简单的一版。** `AGENTOS_IMPROVE=1` 打开后，每隔 `AGENTOS_IMPROVE_INTERVAL` 秒（默认 1800）看一次：没有排队或执行中的任务、并且 `AGENTOS_IMPROVE_IDLE` 秒（默认 600）内没有任务变化，才跑一轮；一轮里每次回放前都检查，用户一提交任务就停下。第 7 节的 cgroup 优先级、电源和负载判断都还没有做。
- **每轮的 token 上限**是 `AGENTOS_IMPROVE_TOKENS`（默认 200 万，`0` 不限），用完时这个候选按“没评完”记下，不会采用。还没有按天的上限。
- **只评测引出候选的任务加最近 20 个可回放的任务**，还没有单独的留出集和金标准清单。
- **线上观察看用户全部任务的成功率**，不是“相关任务”：采用后 20 个任务（或 3 天）内成功率比采用前 30 天低 10 个百分点以上就撤回。这个归因很粗，但只会多撤回，不会多保留。
- **试过没成的任务 7 天内不再试**，避免反复花 token；被用户提交打断的不算试过。
- **还没做的：** 层 C（提示附加段、子 Agent 指令）和层 E（模型路由）；换模型后重新评测（现在只记录了评测用的模型）；通知只在“最近活动”和服务日志里，还没有主动提醒。

建议先做 0 和 1：它们不需要模型、不花钱、不改变系统行为，却回答了最关键的问题——“我们有没有一个可信的评估器”。没有它，后面的阶段都只是在随机改动。

## 10. 风险与未决问题

- **自动生效的风险。** 已决定层 A/B/C/E 过门即自动生效（第 4.1 节）。剩下的风险是评估器本身有盲区：回放测不出依赖上下文的任务，模型的随机性可能让一次侥幸的变好过门。护栏是多次运行、零退化、一次一个加观察期，以及线上退化自动回滚；门槛的具体数字需要在真实使用中校准。
- **评测集偏差。** 历史只覆盖用户做过的事，改进可能过拟合到老习惯；新能力（层 D）的价值回放测不出来，只能靠人判断。
- **数据量。** 新装的机器历史很少，评测不可靠；可以内置一份通用的匿名评测集打底，但不能上传用户数据去构建它。
- **隐私。** 改进流程会把历史任务的内容发给模型。用云端模型时这和日常规划同一个数据去向，但用户应能单独关掉，或限定只用本地模型。
- **模型更换。** 换模型后，针对旧模型调优的提示附加段可能变成负担；附加段应记录它是在哪个模型上评测的，换模型后重新评测。
- **成本失控。** 每日上限之外，每个候选的评测也要有 token 上限；改进器的元评测要把成本算进去。
- **审计膨胀。** 回放评测会产生大量模型调用，它们的用量要记，但评测内部的模拟调用不应写成真实的 `CapabilityInvoked`，否则会污染以后的改进信号；需要单独的评测日志或明确的标记。
