# AgentOS v0.4：让 Agent 成为一等公民

> **状态：五项都已在 v0.4.0 实现，只有第 4 节里“授权本身的参数限定”没有做。** 本文是当时的设计，每节开头注明了实现与设计的差别；实际行为以 [architecture.md](architecture.md) 和 [protocol-v1.md](protocol-v1.md) 为准。

v0.3 把任务内核变成了本地系统服务，但 Agent 仍然是“一句话一个任务、一次只做一件事”的执行器。v0.4 的目标是让它能持续对话、同时做多件事、知道自己花了多少、能被别的 Agent 调用，并在人事先划定的范围内自主行动。

五项工作按依赖关系排序：并发是线程和等待状态的前提；外部 MCP 调用方没有人在场，它免确认能做的事只能由预授权划定，所以放在最后。

| 顺序 | 工作 | 现状（v0.3） |
| --- | --- | --- |
| 1 | 并发执行，运行中可取消（已实现） | 单 worker 串行；取消只在步骤边界生效 |
| 2 | 会话线程与“等待用户补充”（已实现） | 每个意图是独立任务；上下文只来自最近任务摘要和黑板 |
| 3 | 预算、用量和环境信息（已实现） | 只有“最多 8 轮”；用量不记录；系统提示是常量 |
| 4 | 参数级、限时授权与预授权（预授权已实现） | 授权只到“Agent × 能力名”；L2 每次确认 |
| 5 | AgentOS 作为 MCP server（已实现） | 只是 MCP 客户端 |

## 1. 并发执行，运行中可取消

> **已实现。** 实现后的行为见 [architecture.md](architecture.md) 和 [protocol-v1.md](protocol-v1.md)。

**目标。** 多个任务并行推进；一个任务在等模型时，其他任务不排队。取消能打断正在等待的模型请求和可中止的能力调用，而不是等到步骤边界。

**设计。**

- 单 worker 换成有界 worker 池。同一线程（见第 2 节）内的任务保持提交顺序，不同线程之间并行。
- 执行队列的上限和“满时拒绝、不先创建任务”的行为不变；新增“同时运行的任务数”上限，写进协议的资源界限表。
- 每个运行中的任务持有一个取消信号。规划器的模型请求和能力调用都与它竞争：信号先到就放弃等待。
- 能力声明自己是否可中止（`Capability::abortable`，只读能力默认可中止，沙箱插件声明可中止）。不可中止的调用（例如已经发出的外部请求）仍然运行到返回，结果照常记录；任务本身在取消时已经是 `cancelled`。

**约束。**

- 被打断的步骤，结果是“未知”，不是“未执行”，也不假定回滚。任务进入 `cancelled`，该步骤的结果如实写明它在执行中被打断。
- “先落盘再执行”不变：审计的开始标记和任务的运行状态持久化之后才调用能力，并发下每个任务各自遵守。
- 审计日志仍是一条哈希链，只有一个写入者；并发任务的事件在链上交错，每条都带任务编号。
- 黑板已有 `rev` 冲突检测，并发写入靠它拒绝而不是覆盖。

## 2. 会话线程与“等待用户补充”

> **已实现。** 与下文设计的差别：提问做成了内核提供的伪能力 `ask.user`，问题是任务的一步、回答是这一步的结果，所以没有单独的“规划器给出问题”的返回形式；线程历史以文字摘要放进系统提示，而不是作为对话轮次；接着线程说的任务会继承此前任务的污点。实现后的行为见 [architecture.md](architecture.md) 和 [protocol-v1.md](protocol-v1.md)。

**目标。** 后续的话能接着前面的话说；规划器缺信息时可以问，而不是猜或放弃。

**设计。**

- 新增线程：一组有顺序的任务。`submit` 增加可选的 `thread` 字段，缺省时开新线程，所以旧客户端的行为不变。
- 规划时，同一线程里此前任务的意图和结局作为对话历史交给规划器，取代现在“最近 8 个任务摘要”里属于本线程的部分；跨线程的上下文仍来自摘要和黑板。
- 新增任务状态 `awaiting_input`：规划器给出一个问题而不是计划或回答。任务带着问题挂起，不占用 worker，与 `awaiting_confirmation` 的调度方式相同。
- 新增方法 `reply`：对指定任务的当前问题给出回答，任务回到 `planning` 继续，仍是同一个任务。

**约束。**

- **回复绑定具体请求。** `reply` 必须匹配任务和当前这一问，问题换了旧回复就无效。它是变更请求：连接中断后结果未知，客户端只能查询，不能重发。
- **结局如实。** `awaiting_input` 不是结局。用户始终不回答，任务就一直是“等待补充”，取消后是 `cancelled`，不会被标成成功。
- **界面不替用户说话。** 界面展示问题、转交用户的回答，不代答、不提供默认回答。
- 重启语义不变：等待中的任务的规划对话在内存里，重启后标为 `interrupted`。
- 子 Agent 的提问和确认一样，回到人这里，并标明是谁问的。
- 新状态和新方法写进协议文档的兼容性说明；不认识 `awaiting_input` 的旧客户端应把它当作未结束的任务。

## 3. 预算、用量和环境信息

> **已实现。** 与下文设计的差别：子 Agent 的轮数仍来自它的清单，不从管家的轮数里扣，token 和时长则是整个任务共用；预算在每轮规划前检查，不打断进行中的调用；能力内部自己发起的模型请求（例如生成插件草案）和被取消打断的请求没有计量；环境信息里的“界面类型”用的是意图来源。实现后的行为见 [architecture.md](architecture.md) 和 [protocol-v1.md](protocol-v1.md)。

**目标。** 每个任务花了多少是可查的事实；任务不会无限消耗；Agent 知道现在是什么时候、自己在哪台设备上。

**设计。**

- 每个任务有三项预算：规划轮数（现有的 8 轮并入）、token 总量、总时长。默认值由服务配置，子 Agent 的预算从委派它的任务里扣，不另开一份。
- 新增审计事件：每次模型调用结束后记录模型、输入和输出 token 数、耗时，以及它属于哪个任务和哪个 Agent。裁判的调用同样记录。
- 任务上累计用量，随任务一起通过协议读取，新字段带默认值。
- 系统提示从常量改为每轮生成：固定部分之外附上当前时间、时区和设备信息（主机名、系统、界面类型）。

**约束。**

- **超出预算是 `failed`，写明是哪项预算。** 已经完成的步骤保留在任务上；不把“做了一半”写成成功。
- **审计只追加。** 用量事件加进 `AuditEvent`，旧记录必须还能读，`--verify-audit` 对旧日志的结论不变。
- 规划器不报告用量时（规则规划器、不返回用量的兼容接口），记录为“未知”而不是 0。
- 环境信息由服务生成，不是用户输入，也不来自外部内容；不放进任务的 `intent`。
- 等待确认或等待补充的时间不计入时长预算。

## 4. 参数级、限时授权与预授权

> **预授权已实现，授权本身的参数限定没有做。** 实现的是带参数规则和期限的预授权，以及创建、列出、撤销的入口。下文“授权从 Agent × 能力名扩展为可带限定”没有做：授权和子 Agent 清单仍然只到能力名。与设计的其他差别：参数规则是固定的五种匹配而不是 JSON Schema，并且默认严格（没提到的参数不允许出现）；“创建预授权需要确认”落实为设置了 PIN 时必须核对 PIN；“适用于谁”是用户自己或一个已注册的调用方。实现后的行为见 [architecture.md](architecture.md) 和 [protocol-v1.md](protocol-v1.md)。

**目标。** 人可以事先划定一个范围，Agent 在范围内行动不必逐次打扰；范围之外一切照旧。

**设计。**

- 授权从“Agent × 能力名”扩展为可带两种限定：
  - **参数限定：** 对调用参数的约束，例如收件人在给定列表内、路径在给定前缀下。约束不满足等同于没有授权。
  - **期限：** 到期自动失效。
- **预授权**是一条带限定的、由用户明确创建的规则：命中它的调用不再逐次确认。创建预授权本身是一次需要确认的操作，走协议的新方法，并可列出和撤销。
- **预授权写明适用于谁：** 用户自己的任务，或某一个已注册的 MCP 调用方（见第 5 节）。对用户，它免去的是 L2 的确认；对调用方，它免去的是 L1 和 L2 的确认。
- 策略引擎的判断顺序：是否持有授权 → 参数是否满足限定 → 风险分级 → 是否命中预授权 → 污点和裁判。

**约束。**

- **L3 永远不能预授权。** 安装插件、开门锁仍然每次确认加 PIN，与 [self-evolution.md](self-evolution.md) 的规定一致。
- **污点优先。** 任务读过外部内容之后，预授权不再生效，有副作用的步骤仍需确认。
- **撤销立即生效。** 与批准一样，执行时重新检查；已撤销或已过期的预授权不会被进行中的任务继续使用。
- **不跨主体。** 给用户的预授权不适用于任何调用方，给一个调用方的也不适用于另一个；没有“适用于所有人”的预授权。
- **调用方的预授权必须带参数限定或期限，** 并且不能超出它的清单。参数限定是调用方自己被注入时的损失上限。
- **只收窄。** 子 Agent 继承的是委派者授权的子集，限定只会更严；子 Agent 和 MCP 调用方都不能创建预授权。
- **每次命中都留痕。** 策略决定的审计记录里写明用的是哪条预授权；预授权的创建和撤销是新的审计事件。
- **能力不做权限判断。** 参数限定由策略引擎检查，能力只如实声明自己的参数结构和风险等级。
- 裁判仍可把命中预授权的“放行”收紧为“需要确认”。

## 5. AgentOS 作为 MCP server

> **已实现。** 与下文设计的差别：调用方的身份是请求信封里的 `caller` 字段，属于自我收窄而不是认证，没有凭据；调用方不能委派子 Agent（子 Agent 的授权按 Agent 全局设置，并发时可能被用户任务更宽的授权覆盖）；调用方不能写黑板，而不是“写入内容按外部内容对待”；MCP 只支持 stdio，一个进程一个调用方。实现后的行为见 [mcp.md](mcp.md)、[architecture.md](architecture.md) 和 [protocol-v1.md](protocol-v1.md)。

**目标。** 别的 Agent 和工具可以把 AgentOS 当作一个工具来用：交给它一件事，查询进展，读取只读数据。

**设计。**

- 新增一个 MCP server 入口，它是协议 v1 的又一个客户端，不绕过任务服务。
- 暴露的工具对应现有方法：提交意图、读取任务、列出任务、取消任务，以及对只读能力的直接读取。
- **调用方是一个被收窄的主体，不是用户，也不是污点。** 用户注册调用方时给它一份清单，形式与子 Agent 的清单相同：能用的能力和风险上限。清单默认是空的。调用方提交的任务只能在这份清单内规划，实际可用的能力是“清单声明的 ∩ 管家持有的 ∩ 不超过风险上限的”。
- 调用方提交的任务记下它的身份；任务里的每次能力调用都以这个身份过策略引擎。
- 调用方的任务在自己的线程里，线程不与用户的线程混用。

**约束。**

- **同一套策略和审计。** MCP 提交的任务与界面提交的任务走同一个管家循环，没有捷径。
- **来源和污点是两件事。** 来源决定这个任务最多能做什么；污点仍然只表示任务在执行中读过用户控制之外的内容。调用方的任务不因为来源而被标为污染，读了外部内容之后照常被污染。
- **比用户更严的默认值。** 调用方的任务里，清单内的 L1 及以上调用默认都要人确认（用户自己的 L1 是自动执行的）。只有命中绑定到这个调用方的预授权时才免确认，见第 4 节。
- **只读也要在清单里。** 读取的结果会返回给外部 Agent，所以 L0 能力不默认开放；直接读取和任务里的读取都只限清单内的能力。
- **跨任务上下文隔离。** 为调用方的任务规划时，不附上用户的最近任务摘要和黑板，除非清单里声明了 `board.*`。调用方任务的摘要不进入用户之后的规划上下文；它如果获准写黑板，写入的内容按外部内容对待，读到它的任务被污染。
- **调用方只能看到和取消自己提交的任务。**
- **调用方不能批准，也不能回答 PIN。** 需要确认的步骤照常进入 `awaiting_confirmation`，由人在界面上处理，确认问题标明是哪个调用方提出的；调用方看到的是“等待确认”这个事实。`awaiting_input` 的问题可以由调用方回答，因为那是它自己的意图。
- **变更请求不自动重发。** MCP 工具调用超时或断开后，结果未知；调用方应查询任务，而不是再提交一次。
- **注册、修改清单和撤销都由用户在界面上完成，** 是需要确认的操作并写入审计。撤销立即生效：进行中的任务在下一次策略检查时失去授权。
- 不通过 MCP 暴露批准、调用方清单和预授权的创建与撤销，以及 PIN 相关的任何操作。

## 协议与兼容性汇总

以下都需要写进 [protocol-v1.md](protocol-v1.md) 的兼容性说明：

| 类别 | 新增 |
| --- | --- |
| 任务状态 | `awaiting_input` |
| 方法 | `reply`；预授权的创建、列出、撤销；MCP 调用方的注册、列出、修改清单、撤销 |
| 请求字段 | `submit.thread`（可选，缺省开新线程） |
| 任务字段 | 所属线程、当前问题、累计用量、提交来源（均有默认值） |
| 资源界限 | 同时运行的任务数；每任务的 token 与时长预算 |
| 审计事件 | 模型用量；预授权的创建、命中、撤销；用户回复；调用方的注册、清单修改、撤销 |

请求里的未知字段仍然一律拒绝。

## 未决问题

- 是否需要持久化规划对话，使 `awaiting_input` 的任务能跨重启恢复；线程历史是否要从文字摘要升级为完整对话轮次。
- 授权本身（子 Agent 清单）是否也要能带参数限定和期限；没有设置 PIN 时，创建预授权是否应该被拒绝。
- 是否需要本机之外的传输（HTTP），那时调用方身份必须是真正的认证而不是自我收窄；调用方能否在隔离授权的前提下委派子 Agent、写黑板。
- 用户能否按任务放宽预算；能力内部的模型请求如何计量。
- Web Shell 是否按线程组织页面。现在只有终端工作台和桌面会接着线程说。

## 不在范围内

- 能力进程监督、manifest 和 Linux 资源隔离。[v0.3 设计](v0.3-design.md)的“后续”把它们列为 v0.4 的方向；本文不包含，能力仍与服务同进程运行。
- 中断后的安全自动恢复。它需要能力幂等和外部结果查询的契约；本文的并发和取消都不依赖它，被打断的步骤一律按“结果未知”处理。
- 定时和主动任务。
- 子 Agent 使用不同模型，或作为独立进程、远程 Agent 运行。
- 把语音迁到任务服务并删除 `agentosd`（见 [architecture.md](architecture.md) 的“尚未合并的部分”）。
