# 架构

AgentOS 是 Linux 内核之上的用户态 Agent OS：人交付意图，系统协调模型、能力、设备和权限，并持续说明执行状态。本文是唯一的架构说明；设计草案的历史版本见 [v0.2 设计](v0.2-design.md)、[v0.3 设计](v0.3-design.md)和[AgentOS 架构设计草案](https://claude.ai/artifact/RzRDjHkBbJVbnyFDRSZ4BN)。v0.4 的设计见 [v0.4 设计](v0.4-design.md)。

## 基础决策

- **底座：** Linux 内核与现有驱动；Rust 实现用户态 Agent OS 层，不自研内核。
- **首个目标平台：** x86-64 桌面工作站；开发时也支持 macOS。
- **模型：** 以云端为主（Claude API），兼容 OpenAI 格式的接口（其他云服务或本地 Ollama/vLLM），另有离线规则规划器。
- **用户：** 单个系统用户，多个客户端。Unix peer credentials 提供本机账户身份。
- **任务归后台服务所有。** 界面和临时连接不拥有任务的生命周期。
- **模型只负责规划。** 任务事实、授权、人工批准和执行由运行时掌握。

## 一个内核

`agentos-taskd` 是任务内核。所有界面都是它的客户端，通过[本地控制协议 v1](protocol-v1.md) 与它通信。

```
  终端 CLI / 工作台      Web Shell（浏览器）      原生桌面 agentos-shell
        │                       │                         │
        └───────────── 协议 v1（Unix socket）─────────────┘
                                │
                         agentos-taskd
        ┌───────────────────────┼───────────────────────────┐
     任务内核                管家循环                   系统服务
  agentos-runtime      规划 → 策略 → 执行           agentos-services
  （持久任务、分页、   agentos-planner            能力注册表、子 Agent、
    变更通知）         agentos-policy              黑板、裁判、PIN、MCP、
                       agentos-audit               插件、智能家居
```

| Crate | 职责 |
| --- | --- |
| `core` | 词汇表：意图、感知、表达、能力、风险等级、设备 trait |
| `runtime` | 持久任务：稳定编号、状态、步骤、revision、分页、变更通知、取消与重启中断 |
| `ipc` | 协议 v1：版本、请求关联、有界 JSON Lines 帧、结构化错误、本机路径约定 |
| `policy` | 策略引擎：能力授权（grant）、风险分级确认、污点 |
| `audit` | 只追加审计日志：同步落盘、单一写入者、哈希链 |
| `planner` | 规划契约（多轮）、离线规则规划器、Claude 与 OpenAI 兼容规划器 |
| `services` | 能力注册表、感知与表达中枢、子 Agent 清单、黑板、裁判、PIN、MCP、插件与自我进化、Home Assistant |
| `taskd` | 守护进程 `agentos-taskd`：管家循环、内置时钟与笔记、控制服务、按住说话与朗读、崩溃报告、旧数据迁移 |
| `cli` | `agentos` 命令与终端工作台；也是其他客户端复用的协议客户端 |
| `web-shell` | 浏览器界面 `agentos-web-shell`：本机 HTTP 桥、情景布局、实时语音 |
| `shell` | 原生桌面 `agentos-shell`：把任务变化翻译成页面事件的桥，以及设置助理 |

同一件事只有一份实现：规划器、审计日志、能力注册表和各个能力提供方都在共享 crate 里，守护进程只负责把它们接起来。镜像里只有一个守护进程：`agentos-taskd` 作为桌面用户的 systemd 用户服务（`agentos-taskd.service`）随登录启动，状态在 `~/.local/state/agentos`；图形桌面、文本模式的工作台、`agentos` 命令和 `agentos mcp` 都连接它，开机自检和 `agentos-update` 的自检也都跑它。

## 任务与管家循环

客户端提交意图后，服务先预留队列容量，再持久创建 `task-N` 并入队。请求成功只表示已接收；任务执行与客户端连接互相独立，关闭界面不取消任务。

规划是一个循环：管家规划一轮能力调用，逐步经过策略引擎执行，把结果交还给规划器，由它规划下一轮或给出回答。每轮的步骤追加到任务上，所以客户端看到的是真实进度。系统提示末尾附上由服务给出的当前时间、时区、设备和意图来源；时间取自这一段执行开始的时刻（任务开始，或等到批准、回答后继续），同一段执行里各轮的系统提示一字不差，模型服务的提示缓存才能沿用。

- **状态：** `queued → planning → running → succeeded / unhandled / failed`；策略可使任务进入 `awaiting_confirmation`；Agent 提问使任务进入 `awaiting_input`；取消进入 `cancelled`；服务停止或重启把未完成任务标为 `interrupted`，不自动重复执行。
- **结局如实记录：** 真做成了、或规划器直接回答了才是 `succeeded`；规划器没有办法处理是 `unhandled`；规划失败、计划无效、或者最后一轮有调用没成功是 `failed`。规划器在一步失败后换了办法并做成，任务仍然成功。
- **原样交给规划器的结果有上限：** 一次调用的结果超过 2 万字时，规划器只看到开头和结尾，中间写明省略了多少字。完整结果照常记在任务步骤和审计日志里。
- **原地打转就停：** 规划器连续两轮发出同样的调用（同样的能力、同样的参数）并得到同样的结果，第三次再要同样的调用时不再执行，这个 Agent 以失败结束，写明规划陷入了重复。管家打转则任务失败；子 Agent 打转则委派它的那一步失败。只重试一次不算打转。
- **模型的推理接着用：** Claude 在工具调用之间的推理块随下一轮请求原样交回，模型能接着上一轮的思路。只有在系统提示和工具都没变的那几轮才交回（推理块绑定它产生时的上文），之前的推理从前面整段去掉；服务仍拒绝时，去掉全部推理块重发一次。推理块只在内存里，和规划对话一样不落盘。
- **提示缓存：** Claude 规划器把工具与系统提示、以及对话到目前为止的部分标为可缓存，下一轮从缓存读取；每次模型请求读了多少缓存记在审计的 `ModelUsage` 里（`cached_input_tokens`，服务没有报告时不写）。OpenAI 兼容的服务会自动缓存相同的前缀，报告了的也一样记录。
- **步骤：** 每步有唯一 `id`、调用它的 Agent、状态（`pending`、`running`、`succeeded`、`failed`、`skipped`）和结果。一步失败后，同一轮里排在它后面、还没执行的步骤标为 `skipped`，因为它们可能依赖它。
- **只读调用一起执行：** 一轮里紧挨着的只读、可中止的调用同时执行，不必一个等一个。每个调用照样单独过策略，策略决定和审计的开始标记、任务的运行状态都在任何一个开始之前落盘；结果按顺序逐个记录，和一个一个执行时一样。其中一个失败时，同时执行的其他调用照实记成功或失败，之后还没执行的才标为 `skipped`。取消或超时会打断所有同时执行的调用，每个都以 `CapabilityInterrupted` 收尾。有副作用或不可中止的调用仍一个一个执行。
- **整轮预检：** 一轮计划里只要有一个不存在、未授权或参数无效的调用，整轮都不执行。
- **委派：** 管家可以把一步交给子 Agent（能力 `agent.<id>`）。子 Agent 在同一个任务上运行自己的循环，步骤记在委派那一步之后并标上它的名字。它能用的能力只会收窄：清单声明的、委派者持有的、且不超过其风险上限的。子 Agent 不能再委派；确认始终回到人。见 [agents.md](agents.md)。
- **批准：** 绑定任务、步骤、随机令牌、系统用户和五分钟期限。批准后仍重新检查授权，撤销的 grant 不会被批准绕过。等待批准的任务不阻塞其他任务。
- **并发：** 任务在有界的 worker 池上并行执行（默认同时 4 个），互不等待；同一个任务任何时候只由一个 worker 推进。同一线程的任务按提交顺序开始，后一个在前一个结束或挂起之前不占 worker；不同线程之间不保证先后。
- **预算与用量：** 每个任务有三项预算：管家的规划轮数（8 轮；子 Agent 的轮数来自它的清单）、token 总量（默认 200 万，输入加输出，子 Agent 和裁判都算在内）、执行时长（默认 30 分钟，等待批准、等待回答和排队的时间不算）。后两项用 `AGENTOS_TASK_TOKENS`、`AGENTOS_TASK_SECONDS` 设置，`0` 表示不限制。token 和轮数在每轮规划前检查；执行时长是截止时间，规划请求、裁判和可中止的调用到点就被打断（调用记为结果未知），不可中止的调用运行到结束后停下；用完的任务是 `failed`，写明是哪一项，已完成的步骤保留。子 Agent 用完自己的轮数时，失败的是委派它的那一步。每次模型请求的模型、输入和输出 token、耗时都记入审计并累计到任务上；服务没有报告的用量记为未知，不记为 0。
- **线程：** 一段对话是一个线程，用它第一个任务的编号命名。接着线程提交的任务，规划时会拿到线程里此前任务的意图和结局（最近 12 个）。线程只能由开启它的来源继续。
- **提问：** Agent 缺少只有用户知道的信息时调用 `ask.user`。它像能力一样出现在规划器的工具里、经过策略引擎和审计，但由管家自己处理：任务进入 `awaiting_input`，不占 worker；用户的回答成为这一步的结果，任务在原地继续。回答绑定任务、步骤和系统用户，没有期限。子 Agent 的提问同样回到人这里。
- **取消：** 立即生效，不假定已开始的动作回滚。正在等待的模型请求被放弃；能力声明自己可中止（只读能力默认如此，沙箱插件会被终止）时，在途调用也被放弃，这一步记为失败并写明结果未知，审计里以 `CapabilityInterrupted` 收尾。其他调用运行到自己结束，结果照常记录。

持久化的是任务的事实。等待批准或等待回答的任务的规划对话保存在内存里：重启会中断未完成的任务而不是恢复它们，所以不需要恢复对话。

## 风险分级

| 级别 | 例子 | 策略 |
| --- | --- | --- |
| L0 `ReadOnly` | 看时间、读笔记 | 自动执行；可通过 `read` 直接查询 |
| L1 `Reversible` | 记笔记、写黑板 | 自动执行并记录；任务受污染时需确认 |
| L2 `External` | 发邮件、运行场景 | 每次确认 |
| L3 `Irreversible` | 安装插件、开门锁 | 确认 + 身份核验（PIN）；未设置 PIN 时拒绝执行 |

- **外部调用方：** 用户可以注册别的程序（例如通过 MCP 接入的其他 Agent）来提交意图。调用方是被收窄的主体：它的任务以它自己的身份过策略引擎，只能用清单列出、管家持有、不超过风险上限的能力，清单默认为空。它的 L1 及以上调用默认都要用户批准，只有专门给它的预授权才能免去；批准永远由人来做。它只看得到自己的任务，规划时拿不到用户其他任务的上下文，不能委派子 Agent，也不能写黑板。撤销后它立即什么也做不了，它没结束的任务（包括等待批准的）同时取消；之后用同一个 id 重新注册，也拿不回这些任务。`agentos mcp --caller <id>` 把这一切以 MCP server 的形式提供出去，见 [mcp.md](mcp.md)。
- **预授权：** 用户可以事先许可一类调用：一个 L1 或 L2 能力，加上参数规则和可选的期限，符合的调用不再逐次确认。规则默认严格，调用里出现了规则没提到的参数就不符合。它在策略检查的最后才看，只能把“先问人”变成“放行”：不适用于 L3，不适用于被污染的任务，不能绕过缺失的授权，裁判仍可收紧。每次调用都重新检查，所以撤销和过期立即生效；每次命中都记入审计。预授权只能由用户的客户端创建，设置了 PIN 时要核对 PIN；任何 Agent 和能力都不能创建。
- **污点：** 能力可以声明自己的输出来自用户控制之外（联网插件、未沙箱插件、MCP 工具）。任务读到这样的内容后，之后有副作用的步骤都要人确认；子 Agent 的污点会回流到管家。污点属于单个任务，只有一个例外：接着同一线程说的任务会拿到此前任务的结果作为上文，所以此前任务被污染时，它从一开始就被污染。其他线程只知道那个任务发生过，拿不到它的结果。
- **裁判：** 可选（`AGENTOS_JUDGE=1`）。策略直接放行的 L1 及以上步骤，执行前由模型再看一遍；它只能把“放行”收紧为“需要确认”。
- **身份：** 系统用户（UID）是本机账户的信任域，不是 L3 的身份证明。L3 的批准必须带 PIN；PIN 以加盐迭代哈希保存，连续输错会锁定，每次核对都记入审计（不含 PIN 本身）。

## 审计

每个意图、计划、策略决定、能力调用（开始与结果，或被打断）、模型请求的用量、确认、预授权的创建、命中与撤销、调用方的注册与撤销、提问与回答、委派和表达都写成一行 JSON，同步落盘后才继续。每条记录带上一条的 SHA-256，`agentos-taskd --verify-audit` 可检查中间是否有记录被改、删或插入。

日志只在完全有效时才续写。唯一容忍的损坏是崩溃造成的：最后一行写到一半。它会被封口、保留序号并留在链上，由下一条记录为它作证。其他情况下，守护进程把原文件改名保留、另开一份新日志，并在新日志的第一条说明原因；它不会删除或改写旧日志，也不会因此拒绝启动。

## 界面

三个界面都只通过协议 v1 提交意图、读取任务、批准或取消。

- **终端：** `agentos` 命令和实时工作台，适合人和脚本。
- **Web Shell：** 语音优先的浏览器界面，见 [ambient-shell.md](ambient-shell.md)。
- **原生桌面：** `agentos-shell`。协议不推送“计划、步骤、确认”这类页面事件，所以桌面的桥订阅任务变化，读取变化的任务，把它与页面上次看到的样子之间的差别翻译成页面事件。批准用的令牌留在桥里，不交给页面。见 [shell.md](shell.md)。

界面不替用户提交意图：展示数据用 `read` 直接查询只读能力。

## 语音与设备

麦克风和扬声器由服务掌管。界面按住说话时发 `listen`，服务录音（只在按住时，最长 60 秒）、写一条 `device_used` 审计（时长、音频发往哪里），再交给识别后端；识别出的文字作为事件交回发起录音的那个界面，由它像打字一样提交，并标明是说出来的。所以说出来的意图和打字的一样：同一个来源、同一段对话、同样能回答提问，由同一个人批准。说话不能批准任何步骤，批准始终是带令牌的单独请求。朗读是表达中枢的一个输出：`auto` 模式只读说出来的意图的回复。外部调用方不能录音、朗读或订阅语音事件。

服务崩溃时，panic 钩子把报告写进状态目录的 `crash.txt` 并退出，用户服务把它重新拉起；新的一次运行把报告记为审计事件，桌面“最近活动”（协议的 `activity`）里能看到。

## 从 agentosd 合并

v0.5 之前镜像里还有第二个守护进程 `agentosd`，它承载按住说话和崩溃提示，有自己的管家循环、任务存储和 `shell_api` 协议。这些都已迁到任务服务，`agentosd` 已删除：

- **数据：** 桌面用户的任务服务第一次在默认状态目录启动时，把 `~/.local/share/agentos` 里的 PIN、黑板、`mcp.json`、自定义子 Agent 和插件复制过来，笔记从旧的数组格式转换过来。状态目录里已有的不覆盖，旧目录不改动，结果写在状态目录的 `.migrated-from-agentosd` 里。`agentosd` 的任务历史和审计日志不迁移，旧审计日志仍可用 `agentos-taskd --verify-audit --audit <路径>` 校验。
- **升级：** v0.4 及更早版本的 `agentos-update` 要求更新包里有 `agentosd` 并拿它自检，所以更新包里还有一个同名的垫片脚本：它用更新包自己的任务服务完成那次自检，并让重新登录之前的旧桌面会话安静等待。下一个版本删除它。

## 其他边界

- 调用方的身份是“自我收窄”，不是认证：请求带上 `caller` 就只有那个调用方的权限，但本机上以同一系统用户运行的程序可以不带它。它防的是只能通过 MCP 桥说话的 Agent，不是本机上的恶意程序。
- MCP server 只支持 stdio，一个进程对应一个调用方。
- 参数限定只存在于预授权里：授权本身（包括子 Agent 清单）仍然只到“Agent × 能力名”，不能写“这个子 Agent 只能读某个目录”。
- 用量只覆盖规划和裁判的模型请求：能力内部自己调用模型（例如生成插件草案）不计入，被取消打断的请求也没有记录。
- 不可中止的调用（有副作用、又没有声明可中止的）会运行到结束，执行时长预算要等它返回才生效。
- 没有调用超时：不可中止的调用挂住时，被取消的任务仍占着一个 worker，直到它返回。
- 能力与服务同进程运行；插件在 bubblewrap 沙箱里，其余能力没有进程隔离。
- 数据是本地明文；任务历史没有保留期限。每次改动只把那个任务追加到 `tasks.journal`，不再重写整份历史；日志攒到和任务数差不多多时整体并入 `tasks.json`，这次重写的开销仍与历史大小成正比，只是分摊到了之前的改动上。
- 线程的上文是文字摘要，不是完整对话：规划器拿到的是此前任务的意图和结局，不含它们的工具调用和中间结果。
- 只有终端工作台和桌面会接着线程说（工作台用 `/new` 另起一段，桌面的一次运行是一个线程）；Web Shell 的每个意图仍各自成线程，但可以显示提问并回答。
- `Presence` 感知、触觉与环境输出、设备位置只有类型定义。
