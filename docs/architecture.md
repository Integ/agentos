# 架构

AgentOS 是 Linux 内核之上的用户态 Agent OS：人交付意图，系统协调模型、能力、设备和权限，并持续说明执行状态。本文是唯一的架构说明；设计草案的历史版本见 [v0.2 设计](v0.2-design.md)、[v0.3 设计](v0.3-design.md)和[AgentOS 架构设计草案](https://claude.ai/artifact/RzRDjHkBbJVbnyFDRSZ4BN)。下一步的提案（尚未实现）见 [v0.4 设计草案](v0.4-design.md)。

## 基础决策

- **底座：** Linux 内核与现有驱动；Rust 实现用户态 Agent OS 层，不自研内核。
- **首个目标平台：** x86-64 桌面工作站；开发时也支持 macOS。
- **模型：** 以云端为主（Claude API），兼容 OpenAI 格式的接口（其他云服务或本地 Ollama/vLLM），另有离线规则规划器。
- **用户：** 单个系统用户，多个客户端。Unix peer credentials 提供本机账户身份。
- **任务归后台服务所有。** 界面和临时连接不拥有任务的生命周期。
- **模型只负责规划。** 任务事实、授权、人工批准和执行由运行时掌握。

## 一个内核

`agentos-taskd` 是任务内核。所有界面都是它的客户端，通过[本地控制协议 v1](protocol-v1.md) 与它通信。

```
  终端 CLI / 工作台      Web Shell（浏览器）      原生桌面 agentos-shell
        │                       │                         │
        └───────────── 协议 v1（Unix socket）─────────────┘
                                │
                         agentos-taskd
        ┌───────────────────────┼───────────────────────────┐
     任务内核                管家循环                   系统服务
  agentos-runtime      规划 → 策略 → 执行           agentos-services
  （持久任务、分页、   agentos-planner            能力注册表、子 Agent、
    变更通知）         agentos-policy              黑板、裁判、PIN、MCP、
                       agentos-audit               插件、智能家居
```

| Crate | 职责 |
| --- | --- |
| `core` | 词汇表：意图、感知、表达、能力、风险等级、设备 trait |
| `runtime` | 持久任务：稳定编号、状态、步骤、revision、分页、变更通知、取消与重启中断 |
| `ipc` | 协议 v1：版本、请求关联、有界 JSON Lines 帧、结构化错误、本机路径约定 |
| `policy` | 策略引擎：能力授权（grant）、风险分级确认、污点 |
| `audit` | 只追加审计日志：同步落盘、单一写入者、哈希链 |
| `planner` | 规划契约（多轮）、离线规则规划器、Claude 与 OpenAI 兼容规划器 |
| `services` | 能力注册表、感知与表达中枢、子 Agent 清单、黑板、裁判、PIN、MCP、插件与自我进化、Home Assistant |
| `taskd` | 守护进程 `agentos-taskd`：管家循环、内置时钟与笔记、控制服务 |
| `cli` | `agentos` 命令与终端工作台；也是其他客户端复用的协议客户端 |
| `web-shell` | 浏览器界面 `agentos-web-shell`：本机 HTTP 桥、情景布局、实时语音 |
| `shell` | 原生桌面 `agentos-shell`：把任务变化翻译成页面事件的桥，以及设置助理 |
| `agentosd` | 过渡期保留的旧守护进程，见[尚未合并的部分](#尚未合并的部分) |

同一件事只有一份实现：规划器、审计日志、能力注册表和各个能力提供方都在共享 crate 里，守护进程只负责把它们接起来。

## 任务与管家循环

客户端提交意图后，服务先预留队列容量，再持久创建 `task-N` 并入队。请求成功只表示已接收；任务执行与客户端连接互相独立，关闭界面不取消任务。

规划是一个循环：管家规划一轮能力调用，逐步经过策略引擎执行，把结果交还给规划器，由它规划下一轮或给出回答。每轮的步骤追加到任务上，所以客户端看到的是真实进度。最多 8 轮。

- **状态：** `queued → planning → running → succeeded / unhandled / failed`；策略可使任务进入 `awaiting_confirmation`；取消进入 `cancelled`；服务停止或重启把未完成任务标为 `interrupted`，不自动重复执行。
- **结局如实记录：** 真做成了、或规划器直接回答了才是 `succeeded`；规划器没有办法处理是 `unhandled`；规划失败、计划无效、或者最后一轮有调用没成功是 `failed`。规划器在一步失败后换了办法并做成，任务仍然成功。
- **步骤：** 每步有唯一 `id`、调用它的 Agent、状态（`pending`、`running`、`succeeded`、`failed`、`skipped`）和结果。一步失败后，同一轮里排在它后面的步骤标为 `skipped`，因为它们可能依赖它。
- **整轮预检：** 一轮计划里只要有一个不存在、未授权或参数无效的调用，整轮都不执行。
- **委派：** 管家可以把一步交给子 Agent（能力 `agent.<id>`）。子 Agent 在同一个任务上运行自己的循环，步骤记在委派那一步之后并标上它的名字。它能用的能力只会收窄：清单声明的、委派者持有的、且不超过其风险上限的。子 Agent 不能再委派；确认始终回到人。见 [agents.md](agents.md)。
- **批准：** 绑定任务、步骤、随机令牌、系统用户和五分钟期限。批准后仍重新检查授权，撤销的 grant 不会被批准绕过。等待批准的任务不阻塞其他任务。
- **取消：** 在步骤边界生效，不假定已开始的动作回滚。

持久化的是任务的事实。等待批准的任务的规划对话保存在内存里：重启会中断未完成的任务而不是恢复它们，所以不需要恢复对话。

## 风险分级

| 级别 | 例子 | 策略 |
| --- | --- | --- |
| L0 `ReadOnly` | 看时间、读笔记 | 自动执行；可通过 `read` 直接查询 |
| L1 `Reversible` | 记笔记、写黑板 | 自动执行并记录；任务受污染时需确认 |
| L2 `External` | 发邮件、运行场景 | 每次确认 |
| L3 `Irreversible` | 安装插件、开门锁 | 确认 + 身份核验（PIN）；未设置 PIN 时拒绝执行 |

- **污点：** 能力可以声明自己的输出来自用户控制之外（联网插件、未沙箱插件、MCP 工具）。任务读到这样的内容后，之后有副作用的步骤都要人确认；子 Agent 的污点会回流到管家。污点属于单个任务。
- **裁判：** 可选（`AGENTOS_JUDGE=1`）。策略直接放行的 L1 及以上步骤，执行前由模型再看一遍；它只能把“放行”收紧为“需要确认”。
- **身份：** 系统用户（UID）是本机账户的信任域，不是 L3 的身份证明。L3 的批准必须带 PIN；PIN 以加盐迭代哈希保存，连续输错会锁定，每次核对都记入审计（不含 PIN 本身）。

## 审计

每个意图、计划、策略决定、能力调用（开始与结果）、确认、委派和表达都写成一行 JSON，同步落盘后才继续。每条记录带上一条的 SHA-256，`agentos-taskd --verify-audit` 可检查中间是否有记录被改、删或插入。

日志只在完全有效时才续写。唯一容忍的损坏是崩溃造成的：最后一行写到一半。它会被封口、保留序号并留在链上，由下一条记录为它作证。其他情况下，守护进程把原文件改名保留、另开一份新日志，并在新日志的第一条说明原因；它不会删除或改写旧日志，也不会因此拒绝启动。

## 界面

三个界面都只通过协议 v1 提交意图、读取任务、批准或取消。

- **终端：** `agentos` 命令和实时工作台，适合人和脚本。
- **Web Shell：** 语音优先的浏览器界面，见 [ambient-shell.md](ambient-shell.md)。
- **原生桌面：** `agentos-shell --taskd`。协议不推送“计划、步骤、确认”这类页面事件，所以桌面的桥订阅任务变化，读取变化的任务，把它与页面上次看到的样子之间的差别翻译成页面事件。批准用的令牌留在桥里，不交给页面。见 [shell.md](shell.md)。

界面不替用户提交意图：展示数据用 `read` 直接查询只读能力。

## 尚未合并的部分

`agentosd` 还在仓库里，镜像默认仍启动它，原因只有一个：**按住说话的本机语音**（录音、识别、朗读、麦克风指示灯）由它承载，任务服务还不提供。此外只有它有崩溃报告在桌面“最近活动”里的提示。

它的规划器、审计日志、能力、子 Agent、黑板、裁判、PIN、MCP、插件和智能家居都已经改用共享 crate，与任务服务是同一份代码。它自己仍保留一套管家循环和任务存储（检查点恢复语义），以及不带版本的 socket 协议 `shell_api`。这部分是待删除的重复，不要在上面加新功能。

合并的最后一步是：把语音迁到任务服务一侧（需要协议里有麦克风控制和设备使用的审计入口），把崩溃提示接到任务服务，把镜像的会话脚本和自检切到 `agentos-taskd` + `agentos-shell --taskd`，然后删除 `agentosd`。两个守护进程的状态目录不同（`~/.local/share/agentos` 与 `~/.local/state/agentos`），切换时需要迁移笔记、插件、黑板、`mcp.json` 和 PIN。

## 其他边界

- 单 worker：任务串行执行，一个任务在等模型时，其他任务排队（等待批准的任务不占用 worker）。
- 能力与服务同进程运行；插件在 bubblewrap 沙箱里，其余能力没有进程隔离。
- 数据是本地明文；任务历史是全量原子快照，没有保留期限。
- 没有会话线程：每个意图是独立任务，上下文来自最近结束的任务摘要和黑板。
- `Presence` 感知、触觉与环境输出、设备位置只有类型定义。
